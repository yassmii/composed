# Review visual decisions in context

Use for a substantial critique or a comparison of supplied directions. Select relevant dimensions;
do not turn this reference into a mandatory full audit of every component.

## Evidence before verdict

Record the surface, intended task, source and state viewed. A render supports observations about
composition; code supports implementation hypotheses; interacting with the running interface supports
behavioural findings. Mark unobserved dimensions as unknown. A static detector flags patterns, not taste.

## Review dimensions

| Dimension | Useful question | Evidence or intervention |
| --- | --- | --- |
| Product relevance | What could only belong to this product or audience? | Identify a specific image, information relationship, demonstration or voice; replace interchangeable filler. |
| Composition | Does the structure express the content's relationships? | Check priority, grouping, rhythm and scanning; cards are justified by independent units, not a default wrapper. |
| Type | Do roles, scale and line lengths work with real content? | Inspect long headings, numbers, reading measure and loaded fonts; avoid choosing a novelty font to disguise weak hierarchy. |
| Colour | Are identity, emphasis and state distinguishable? | Inspect real combinations and themes; measure contrast where possible, not by eye. Respect pinned brand colours. |
| Images | Does each visual explain, demonstrate or establish identity? | Inspect subject, crop and placement; identify generic stock or a missing product view. Verify source and usage rights before reuse. |
| Interaction | Can the user predict, complete and recover? | Exercise primary action, keyboard/focus, loading and errors; a pleasing mockup is not this evidence. |
| Motion | Does it explain change or contribute to the requested experience? | Check interruption, reduced motion and slower devices. Decorative movement is optional; no universal entrance animation. |
| Content | Does the language name real things and actions? | Check vague headings, repeated claims, labels and recovery instructions. Never supply invented proof as a fix. |
| Adaptation | Does the hierarchy survive narrow layouts and long content? | Compare actual renders; check zoom, overflow, focus visibility and meaningful reading order. |

For web accessibility, assess the applicable standard and component context: normal text usually needs
4.5:1 contrast, large text 3:1, and relevant UI boundaries/state indicators 3:1. Target size is not a
single universal 44px rule: WCAG 2.2 AA has a 24 CSS px criterion with exceptions, while larger touch
targets may be a deliberate usability goal. Native platform units and guidance differ. These checks
are not a complete conformance assessment; note what was measured and what still needs testing.

## Compare without rewarding spectacle

Use the same brief, content, viewport and maturity when comparing options. Judge relevance,
distinctiveness, task clarity and execution separately. Name both the strongest reason for your
recommendation and what it sacrifices. Do not reward a rich illustration merely because the other
option is a wireframe, or infer task success from a preferred screenshot.

Watch for replacement clichés: cream/serif, dark/neon and rigid editorial grids can all become the
same template. Their presence alone proves nothing. Ask which visible choice follows from this brief.
Keep familiar controls familiar; a dense operational screen need not have a spectacular hero.

## Make findings actionable

For each material issue, give location/state, observation, user or brand consequence, a bounded fix
and a way to check it. Label a usability blocker, a craft defect and a subjective preference differently.
For example, “the mobile price and purchase action separate after the feature list; keep the decision
information together and test the narrow layout” is actionable; “make the page feel premium” is not.
Preserve strengths and name the few changes worth doing first. Record limits rather than a fake pass.
